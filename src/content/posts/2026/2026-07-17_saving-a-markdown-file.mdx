A todo application appears to have an unusually small job description. Show a list. Change a square into a square with a tick. Allow the user to experience approximately four seconds of being in control of their life.

Then save the file.

Those last four words contain quite a lot of engineering.

I previously wrote about [building tdx](/posts/2025/11/2025-11-29_building-tdx/), including its move to Go and the benefits of a testable terminal interface. This time I want to look at something less visible: what happens when the Markdown file changes while the application is using it.

## Plain text means other tools are invited

One of tdx's main attractions is that your tasks live in ordinary Markdown. You can keep them in a project, edit them in your preferred editor, and put them in Git.

That also means tdx does not own the file exclusively.

Imagine opening a task list in the terminal interface, then adding a note in your editor. The application still has its earlier view of the file. If it writes that view back without checking, your new note disappears.

Nothing about that failure looks dramatic in the interface. A checkbox might even toggle successfully. The problem is that the app has done exactly what you asked and one additional thing you very much did not ask for.

## A successful write is not necessarily a safe save

There are several separate problems hiding behind the Save button.

An atomic save helps prevent the destination from being left halfway written. External-change detection asks whether the file still matches the version the app started from. A conflict view helps a person understand the difference. History provides another route back when a previous state is needed.

Solving one does not solve all the others. You can replace a file atomically and still replace it with the wrong contents. You can keep snapshots and still make a confusing decision about whose edit wins.

The user should not have to know those terms to benefit from them. They should be able to use their editor and their todo tool without treating the file like a diplomatic incident.

## Recovery should be something you can inspect

The 0.13 release line includes file version history: content-addressed snapshots, a way to compare versions, and a restore flow. The command palette's `:versions` view makes that history accessible from the interface.

The useful part is not merely “there is a backup somewhere.” It is being able to see what changed before restoring it.

For example, an older version may contain a sentence you want back and several completed tasks you do not want to undo. A diff makes the decision concrete. A timestamp alone mostly tells you when to feel suspicious.

Snapshots also have a different job from Git. They can help with local editing recovery, but they are not a replacement for a repository history or a backup strategy.

## Preserve more than the checkboxes

Markdown task files are rarely just tasks. They contain headings, links, notes, code blocks, and the spacing that makes them comfortable to read.

A tool that treats the whole document as disposable wrapping around its checkboxes will eventually become an unwelcome collaborator. The app needs to make a small change while respecting the surrounding file.

This is where the earlier work on parsing and testable behavior continues to pay off. The interesting cases are concrete: an external edit, a changed task, a restore, a document containing syntax that merely looks like a task. These are better questions for tests than “does the happy-path screenshot still look nice?”

## Trust is a feature you notice when it is missing

It is tempting to judge a small tool by how many commands fit in its README. But file-based tools also need to earn the right to touch your files.

For me, that makes saving behavior part of the product itself. The goal is for the user to think about their tasks, not maintain an emergency copy before checking one off.

There are already enough ways to avoid doing a todo. Protecting the todo list from the todo application should not be another one.
