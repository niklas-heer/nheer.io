I want writing a little command-line tool to be easy. I also want giving it to somebody else to be easy. These are, annoyingly, two different wishes.

Python is lovely for the first part. For the second, I would like to hand over one small executable and say: “Run this.” No Python installation, no virtual environment, no conversation about which `pip` belongs to which interpreter.

That is the idea behind [Kipferl](https://github.com/niklas-heer/kipferl): **Python-style code, packaged into a small standalone application.**

How small? The status app below—with a box, a table, and colored output—builds to **1,467,617 bytes on Apple Silicon. About 1.47 MB.**

The coffee service is fictional. The executable size is not.

## The interesting part is what you ship

Putting a Python program into an executable is an established idea. The challenge I wanted to work on was the combination: a pleasant high-level language, useful terminal UI components, and an output file small enough to feel appropriate for a small tool.

A five-line script should not need a removal company.

Kipferl uses PocketPy, an embedded Python implementation, with a Rust host and a curated set of modules for command-line applications. It packages the program with the runtime it needs. It does **not** turn arbitrary CPython code into native machine code, and it does not promise compatibility with every package on PyPI.

That trade-off is central to the size. The product is a focused way to build CLIs, rather than a suitcase containing an entire Python installation.

## A small app that does something visible

This is the complete program in the recording:

```python
import tui

tui.box("Three services. One small executable.", title="Release check")
tui.table([
    ["Service", "Status"],
    ["api", "ready"],
    ["worker", "ready"],
    ["coffee", "critical"],
], headers=True)
tui.success("Application ready. Coffee needs attention.")
```

Build it, then run the result:

```sh
kipferl build status.py -o status
./status
```

The person receiving `status` does not need Kipferl or Python installed. The executable still targets a particular operating system and architecture; “standalone” does not mean the same file runs on every machine.

## Leave the unused capabilities at home

Kipferl 0.6 examines imports and conservatively chooses a prebuilt runtime profile. The status app fits the smaller **core** profile. Building that exact same source with `--full-runtime` includes the complete runtime instead.

<BinarySize />

These are measured outputs of the example above using the released 0.6.0 builder on macOS ARM64. MB means one million bytes. Source, runtime profile, and target platform affect the result; 1.47 MB is an example you can reproduce, not a ceiling for every application.

The [0.6 release notes](https://github.com/niklas-heer/kipferl/releases/tag/v0.6.0) recorded a separate minimal-app baseline of 1,450,837 bytes. The larger command-line **builder** is another artifact again: it is not the file you distribute to your users.

This is profile selection, not a promise that every unused function disappears individually. When the analyzer cannot safely choose the smaller profile, keeping the required functionality matters more than winning a few bytes.

## Small enough to give away casually

For me, the appeal is practical. A repository helper, a status report, a little interactive utility: things that are useful enough to share, but should not become installation projects of their own.

I want the easy part of writing Python and the easy part of distributing a small native tool to meet in the middle.

Kipferl is named after a pastry. Ideally, the application should be about as troublesome to hand to somebody.
