I used zsh for a long time. I tried Fish and wandered through a few other shells, as one does when the actual task is insufficiently distracting.

Then I found Nushell and made it the default in the terminals I use.

Working with data felt wonderful. CSV and JSON stopped being things I had to disassemble with increasingly elaborate text processing. I could inspect rows, select fields, filter values, and keep drilling into the result. Even a directory listing became something I could ask questions of.

Then I copied a command from my notes.

It did not work.

## The clipboard kept sending me back

The same thing happened with commands from the internet and from sessions with AI tools. They assumed familiar shell syntax. My new default shell had different rules.

Those rules were part of what made the data experience so useful. But I kept switching back to a traditional shell to run the command I had just copied. I wanted the new capabilities without making the clipboard a compatibility negotiation.

I had also spent some time with Xonsh. The idea of using Python—a real, general-purpose programming language—inside a shell appealed to me. For scripts and customization, I would rather use a language with a life beyond configuring my prompt.

Eventually the wish list became fairly clear:

- Keep a familiar mode for everyday commands and Bash/zsh habits.
- Switch to a data mode when I actually want to work with data.
- Use a general-purpose language to script and extend the shell.

[Quirl](https://github.com/niklas-heer/quirl) is my attempt to put those things in one place.

## Watch the same session change gears

The first command is deliberately unremarkable:

```sh
printf 'api\nworker\njobs\n' | wc -l && echo 'pipeline: healthy'
```

A familiar pipe, a count, and a command that runs if the pipeline succeeds. That is the point. Not every trip to the terminal should require a new worldview.

Quirl's native normal mode covers a defined core of shell behavior. It is not a complete Bash or zsh implementation, so dialect-specific syntax has an explicit home:

```sh
bash { cat <(printf 'Bash still works.\n') }
```

There are zsh blocks too. The goal is to make existing habits usable while keeping it clear which language is interpreting a command.

## When I want data, I ask for data

Type `mode data`, and a command like this can work with the fields in a JSON file:

```text
open services.json | where latency > 50 | select service latency
```

In the recording, the result contains the services whose numeric latency exceeds 50. No counting columns. No guessing which run of spaces belongs to the table formatting.

This is the part of the structured-shell experience I wanted to keep: exploring data should feel like exploring data. CSV files, JSON documents, and structured listings are natural places to use it.

Type `mode normal` when you want to go back. Both modes earn their place by being useful at different moments.

## Lua is the third ingredient

For the extension language, I ended up choosing Lua rather than Python.

I spent time looking for something fast and embeddable. Lua fit that goal, and Quirl already uses it for configuration, scripts, and extensions. Rust handles the shell's core; the embedded Lua runtime has explicit resource limits.

You can try it without writing a configuration file:

```lua
lua return { answer = 6 * 7, language = _VERSION }
```

That is a tiny example, but it shows the boundary: when I want to program the shell, there is a programming language available. I do not need to stretch a configuration format into one.

Quirl means a whisk. I wanted to mix familiar commands, structured data, and an extension language into a shell I would enjoy using. The [0.1 release](https://github.com/niklas-heer/quirl/releases/tag/v0.1.0) is an early implementation of that vision on Linux and macOS.

Mostly, I would like to spend less time explaining my clipboard to my terminal.
